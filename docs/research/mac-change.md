# mac-change

## SUMMARY

1) B1:21:81 is not an IEEE OUI. The Wireshark registry generated from the IEEE MA-L/MA-M/MA-S/CID/IAB lists has no entry starting with 0xB1, and only two entries in the whole registry have an odd first octet. 0xB1 = 1011 0001b, so the I/G bit is 1 (a group address in IEEE terms) and the U/L bit is 0. No vendor can be assigned an OUI like that. The firmware simply invented this prefix. 2) It is not an LE privacy or random-static address either. BR/EDR (A2DP, AVRCP, HFP, RFCOMM all work on the new address) has no random addresses. Read as an LE random address, the two top bits are 0b10, which is the reserved subtype (static needs 0b11, a resolvable private address 0b01). BlueZ reports AddressType 'random' only for LE random addresses (bluez src/device.c:1003-1016). So the "random static / privacy?" hypothesis in HANDOFF 5.8 is wrong. 3) The same prefix appears on someone else's unit: B1:21:81:B1:F0:84 in divoom-minitoo-osx. So B1:21:81 is a shared Divoom provisioning prefix, not a fingerprint of our speaker. 4) The Bluetooth host stack is JieLi. The FE010000-1234-5678-ABCD-00805F9B34FB 'JL_SPP' record on RFCOMM channel 10 is byte-for-byte the JieLi SDK record. The DID vendor 0x05D6 is Zhuhai Jieli, and the USB side reports itself as the JieLi chip family 'BR28'. This conflicts with the minitoo-forth claim that the main chip is an Actions ATS2831, at least for the Bluetooth part. 5) In the JieLi BR28 sound-box SDK the address is read from config/flash. If it is missing, all 6 bytes are regenerated at random and written back, so a stock JieLi regeneration would NOT keep B1:21:81. The Actions SDK does exactly 'vendor prefix + 3 random bytes', which matches what we observed, but nothing proves MiniToo runs that code. So either Divoom customised the generator or this was not a stock regeneration. 6) The name change can be explained purely by BlueZ. BlueZ keeps one Name per device object and overwrites it with any complete name it hears in inquiry, LE advertising or connection data. It merges LE-public and BR/EDR devices with the same address. The AVRCP input device takes that Name at AVRCP-connect time plus ' (AVRCP)'. So 'MiniToo-App (AVRCP)' only means BlueZ's Name was '...-App' at that moment. There are two candidate sources: a BLE advertisement from the same address, or the firmware renaming its classic name. Strong but indirect evidence says a BLE side exists: the 49535343-FE7D… transparent-UART service and GAP appear in the device's UUID list, the Divoom iOS app controls MiniToo, and the sibling Timebox Evo uses exactly that GATT service from the official iOS app. 'MiniToo-App' was not found anywhere on the web. 7) minitoo-autoaddr's 'most frequent address' does not measure liveness. It counts the address in '[CHG] Device X RSSI' lines from bluetoothctl. BlueZ emits those only on RSSI jumps of 8 dB or more, folds a new device's first RSSI into its creation signal (printed as [NEW], so not counted), and emits 'RSSI is nil' for every found device when the scan stops. With two candidates the pick is close to arbitrary and can flip-flop, and each flip re-pairs, rewrites config and restarts hermes-minitoo. 8) Other autoaddr defects. The fixed PREFIX filter would miss a fully random new address and can match another Divoom unit. It starts a 12 s scan on every transient disconnect, including the profile-switch drops in HANDOFF 5.2/5.7. It drives bluetoothctl through stdin with fixed sleeps. Its success check requires Paired=yes, although the device is known to drop its pairing. 9) The str.replace rewrite only touches colon-form strings. In every WirePlumber 0.5.x except 0.5.13 the A2DP sink is named bluez_output.B1_21_81_A0_78_53.1 (underscores, '.1'), while the HFP loopback source is bluez_input.B1:21:81:A0:78:53 (colons). So audio.output may silently go stale. WirePlumber then falls back to the default sink because pw-play does not set node.dont-fallback, which is consistent with HANDOFF 8.9's 'it works by accident'. 10) Design proposal. Identify the speaker through BlueZ D-Bus snapshots (busctl --json GetManagedObjects): Modalias prefix bluetooth:v05D6p000A (shared with Tiivoo 2, so combine it with the name), name ~ MiniToo, BR/EDR evidence (Class, A2DP/SPP/JL_SPP UUIDs), reject AddressType=random. Do not hard-require the prefix. Scan BR/EDR only (bluetoothctl --timeout N scan bredr), after a reconnect grace period and with backoff. Act only on one unambiguous candidate seen twice. Pair, Trust and Connect through busctl (with no agent BlueZ uses NoInputNoOutput). Update config.json as JSON and resolve the PipeWire node names from pw-dump. In talk-key, match the input device by Bus=0005 Vendor=05d6 Product=000a, which BlueZ copies into the AVRCP input device, instead of by name. 11) Without hardware it remains unknown whether CB:09 still exists alongside A0:78:53, what triggered the change (Divoom-app firmware update, reset, corrupted config storage), and whether '-App' is a BLE or a classic name. Exact commands to settle these are listed below. 12) Making the speaker keep a stable address is not feasible from the host. The address is chosen and stored by the speaker's firmware, there is no protocol to set it remotely, and custom firmware is blocked: no source, no working flash route, the chip itself is disputed, and there is a brick risk.

def find_event():
    blocks = open('/proc/bus/input/devices').read().split('\n\n')
    def ev(b):
        m = re.search(r'\bevent(\d+)\b', b)
        return f'/dev/input/event{m.group(1)}' if m else None
    for b in blocks:  # primary: BlueZ uinput carries DID ids (avctp.c:1203-1206)
        bl = b.lower()
        if 'bus=0005' in bl and 'vendor=05d6' in bl and 'product=000a' in bl and '(avrcp)' in bl:
            p = ev(b)
            if p: return p
    for b in blocks:  # fallback: old heuristic
        if 'MiniToo' in b and '(AVRCP)' in b:
            p = ev(b)
            if p: return p
    return None

def score(p):

        return -1  # LE-only identity
    s = 0
    if str(p.get('Modalias', '')).lower().startswith('bluetooth:v05d6p000a'): s += 4

(2) If exactly one other candidate is Connected in two consecutive checks: adopt it.
(3) If now - last_ok < 180 s: do nothing, so BlueZ, WirePlumber and the RFCOMM backoff can reconnect.
(4) If now >= next_scan: run `bluetoothctl --timeout 20 scan bredr` with Popen, sleep 17 s, take devices() WHILE discovery is still running (RSSI is cleared on stop, adapter.c:1711-1731), then wait for the process. seen = candidates with an 'RSSI' key. Backoff 5 → 10 → 20 → 60 min.
(5) If the configured address is in seen: just call Connect on it, no re-pair.
(6) If exactly one non-configured candidate is seen in two consecutive scans: adopt it. If two or more: log Name/Class/Modalias/AdvertisingFlags for each, notify, and take no action.

adopt(path):
- if not Paired: busctl --system --timeout=45 call org.bluez <path> org.bluez.Device1 Pair (no agent = NoInputNoOutput; the speaker must be pairable).
- busctl --system set-property org.bluez <path> org.bluez.Device1 Trusted b true
- busctl --system --timeout=45 call org.bluez <path> org.bluez.Device1 Connect
- Poll until Connected and ServicesResolved (up to 30 s), then call the JSON-aware config update. Success means Connected, NOT Paired.
- Optional, opt-in: after 24 h of working on the new address, call Adapter1.RemoveDevice on the old object path.

Unit: ExecStart=/usr/bin/python3 -I %h/hermes-minitoo-gadget/scripts/minitoo-autoaddr.py, After=bluetooth.target. Never run a scan while minitoo-talk-key is in phase 'recording' (share a flag file).
  RISK: Low. Pair/Trust/Connect are standard operations. The risk of binding to a neighbour's Divoom is reduced by the 'exactly one candidate, seen twice' rule. Nothing is written to the speaker.

## UNSOLVABLE
- (Making the MiniToo keep a fixed Bluetooth address, or setting its address from the Linux host.) The address is chosen by the speaker's firmware and stored in its own flash: JieLi keeps CFG_BT_MAC_ADDR in its flash key-value store or factory config area and regenerates it when missing (user_cfg.c:392-406); the Actions SDK keeps it as a factory property (bt_manager_check_mac_name.c:154-174). No HCI, LMP or profile mechanism lets a remote host set another device's address. The only setter seen in the SDK, bt_update_mac_addr / JieLi factory test-box path (user_cfg.c:101-121), uses a JieLi production-test protocol that is not public. Custom firmware is not practical: (1) no source for Divoom's build, so it would be binary patching of flag41007.bin; (2) all known delivery routes are blocked or unproven: Bluetooth-serial update has a 'catch-22', SD is closed, USB DFU topology unclear, JTAG needs the case opened (research/FIRMWARE.md:58-100); (3) the target chip is disputed: the SDP and USB evidence says JieLi BR28, minitoo-forth says Actions ATS2831; (4) high brick risk with no confirmed recovery path; (5) even minitoo-forth's custom code ran only in simulation (FIRMWARE.md:54).
  WOULD CHANGE: A verified chip identification (board photos or chip markings) plus a working, recoverable flash route (DFU or JTAG). Or Divoom fixing the firmware. Or the JieLi test-box address-write protocol being reverse-engineered and confirmed safe.
- (Determining from source alone what triggered the 8 Oct address change, and whether the old address is gone or still active as a second identity.) Divoom's firmware and configuration are closed. The stock JieLi path (6 random bytes) contradicts the preserved B1:21:81 prefix, while the matching Actions path contradicts the JieLi SDP evidence, so the generator in Divoom's build is unknown. The trigger (firmware update via the Divoom app, button reset, storage corruption, deep discharge) leaves no trace on the host except possibly a changed Modalias version and BlueZ cache timestamps.
  WOULD CHANGE: The diagnostic commands below (scan bredr for both addresses, compare cached Modalias/info files, btmon of a scan), and the user saying whether the Divoom app updated or reset the speaker on 8 Oct. Ideally, an HCI capture of an official update followed by a check of the address.
- (Deciding without hardware whether 'Divoom MiniToo-App' is a BLE advertising name merged into the classic device object or a renamed classic name, and what 0xAF30 / 49535343-FE7D… are attached to.) Both mechanisms produce the same BlueZ-visible Name (adapter.c:7459-7460, device.c:5442-5455). The UUID list mixes SDP, inquiry data, LE advertising and GATT sources, and bluetoothctl info does not say which radio a UUID came from.
  WOULD CHANGE: `btmgmt find` or btmon showing LE advertising reports (address type, name, flags) vs inquiry results; `sdptool browse`; whether AdvertisingFlags exists on the object; the SupportedTechnologies line in /var/lib/bluetooth/<adapter>/<addr>/info.

### solution concerns
- The audio.* fields are not only PipeWire targets for minitoo-talk-key. hermes-minitoo passes them to the Hermes Gadget SDK: config.py:51-58 (sdk_config) → hermes_gadget/linux/client.py:118-119 → audio.py:18-30. The SDK resolves them through sounddevice/PortAudio device-name matching and enables mic/speaker only if the keys exist. The proposal's long-term step, 'drop the stored node names and resolve at call time in talk-key', would therefore disable the gadget's speaker and mic paths. Writing pw-dump node names (for example the underscore '.1' form after a future WirePlumber upgrade) into config could also make the SDK's check() fail at startup. sounddevice raises ValueError on 'no device matching', and check() only catches PortAudioError (audio.py:25-29). How the current colon-form strings resolve in PortAudio on the server was not checked by the report, and I could not check it either.
- The JSON-rewrite proposal is fine, but its stated motivation ('audio.output is stale') is wrong for Ubuntu 26.04 / WirePlumber 0.5.13 (see the node-name finding). The real risk comes after a WirePlumber upgrade to 0.5.14 or later, when the sink becomes bluez_output.B1_21_81_….1. Run `wireplumber --version` before changing anything.
- In find_event, 'pick the highest event number' does not mean 'newest'. The kernel reuses the lowest free input minor. A Bus=0005 05d6:000a match also matches a Tiivoo 2 or any other JieLi device that keeps vendor 0x05D6 / product 0x000A in its DID.
- A user unit with `After=bluetooth.target` does not order against the system bluetoothd; the user manager cannot depend on system units. Use a retry loop instead.
- `bluetoothctl --timeout N scan bredr` stops our OWN scan from feeding LE advertisements into Name. It does not stop BlueZ background passive LE scanning or another client's scan from overwriting Name (adapter.c:7459-7460). The claim 'LE advertisements cannot overwrite Name' is too strong.
- PreferredBearer needs Experimental mode, via -E or main.conf Experimental=true. That turns on every experimental BlueZ D-Bus interface on the server, so it is a system-wide change that needs root. It is useless once the BR/EDR side is bonded, because select_conn_bearer already prefers the bonded bearer (device.c:2639-2641).
- Pair with 'no agent' uses the system default agent if any is registered (agent.c:257-258). A leftover or desktop agent would change the IO capability.
- Diagnostics: `ls -ld --time-style=full-iso` shows the directory mtime, which changes on every info/cache rewrite, not its creation time; use `stat -c %w` for birth time. `bluetoothctl disconnect` interrupts the running hermes-minitoo RFCOMM link and audio, and the speaker may page back to the host instead of becoming discoverable. Run the diagnostics with hermes-minitoo stopped too, not just autoaddr. `journalctl -u bluetooth` needs adm or systemd-journal group membership.
- Backoff of 5→60 min combined with 'seen in two consecutive scans' plus a 180 s grace period can delay adopting a legitimately changed address by an hour or more. State this trade-off explicitly or make it configurable.
- The proposed state machine should not scan at all while ANY MiniToo candidate is connected, not only during 'recording'. A BR/EDR inquiry steals radio time from active A2DP, SCO and RFCOMM links.
