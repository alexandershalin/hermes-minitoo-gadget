# hfp-button

## SUMMARY

I traced the BlueZ 5.85 and PipeWire 1.6.2 sources, which are the same versions the server runs. BlueZ cannot be what drops the presses. AVCTP PASSTHROUGH goes to uinput with no SCO or HFP condition anywhere in avctp.c or avrcp.c. The only diversion is a registered AVRCP target player, and that would also kill presses in A2DP mode, which is not what we see. So while SCO is up, the speaker itself stops sending AVRCP. Hypothesis 2 in the HANDOFF is right in substance. The likely reason is that PipeWire fakes a phone call. On every SCO acquire it sends "+CIEV: 2,1" (call active) to any HF that enabled indicators with AT+CMER (backend-native.c:2808-2811, 1067-1081). It sends "+CIEV: 2,0" only on transport release. A HF that thinks a call is active normally maps a short press of the multifunction button to AT+CHUP (hang up) instead of AVRCP PLAY/PAUSE. In AG mode PipeWire handles neither AT+CHUP nor any unknown command (AT+BVRA, AT+CKPD, AT+NREC, ...). With no ModemManager modem, which is the default, all of them reach one branch. That branch logs at INFO, "RFCOMM receive command but modem not available: <cmd>" on topic spa.bluez5.native (backend-native.c:1432-1435). It replies "+CME ERROR: 1" or "ERROR" and changes no state. Nothing leaves the process: no node prop, no D-Bus, no telephony object, since that object exists only in the HF role. WirePlumber's default level is N (notice), which hides INFO. That explains why nobody has ever seen the press. INFO can be enabled for that one topic at runtime, without root and without restarting WirePlumber: `wpctl set-log-level "N,spa.bluez5.native:I"`. That topic has no per-packet logging, so even level D does not flood. The setting reaches the plugin through module-log-settings → wp_log_set_level → pw_log_set_level_string. A non-root detector is then simple: a thread in minitoo-talk-key.py follows `journalctl --user -u wireplumber -f -o cat` and treats AT+CHUP, AT+BVRA, ATA, AT+CKPD, AT+BLDN or ATD as a button press. This fixes 5.3 if the speaker really sends AT+CHUP, which only a hardware test can confirm. The speaker's volume keys, if they send AT+VGS or AT+VGM in call mode, already show up without any debug as node volume changes in pw-dump, pw-mon and wpctl. A second experiment is to set the runtime device param bluez5.disable-dummy-call=true. Then the speaker no longer believes it is in a call and may send AVRCP again during SCO, which would need no new code. The risk is that it drops SCO without a call, which is the reason the fake call exists. Two HANDOFF claims are wrong. BRSF 671 decodes to EC/NR, 3-way, CLIP, voice recognition, remote volume, codec negotiation and eSCO S4; it does NOT include enhanced call status/control or HF indicators. And the AT+CKPD=200 handler that was found in libspa is HSP-only, which is disabled and which the MiniToo does not offer. For 5.5 the script has several windows where a press is lost by design: the whole "starting" phase, the time while `button release` runs, a 1 s debounce counted from the end of the recording, a 3 s reopen gap, and opening only the first matching input device. There is also a likely device-side window: after VAD stops, the speaker stays in "call" mode until WirePlumber restores A2DP (restore timeout 2000 ms plus teardown, ~6 s measured), and a press there is presumably also AT+CHUP. vad_wait also checks stop_evt only after a blocking read returns, so a stop is not honored if SCO audio stalls. A firmware change to the speaker's in-call key mapping is not feasible. There is no proven delivery route, the main SoC (Actions ATS2831) is NDA and has no SDK, and nothing proves recovery after a bad flash. It is also probably unnecessary if the AT watcher sees the press. Nothing here was tested on hardware; every speaker-behaviour claim is a hypothesis until the owner runs the diagnostics.

- (5.1 / 5.3) [implement-now-safe] hw_test=True
  APPROACH: No-root AT-command watcher. Raise only spa.bluez5.native to INFO and follow WirePlumber's user journal from minitoo-talk-key.py. Treat call-control AT commands from the speaker as Play/Pause.
  IMPL: 1) Turn on the log, once and without root: `wpctl set-log-level "N,spa.bluez5.native:I"` (works now, no restart). For persistence across WirePlumber restarts, ship scripts/wireplumber/60-minitoo-hfp-at-log.conf → ~/.config/wireplumber/wireplumber.conf.d/ containing `context.properties = { log.level = "N,spa.bluez5.native:I" }`. That takes effect at the next WirePlumber start and only if WIREPLUMBER_DEBUG is unset. 2) In minitoo-talk-key.py add a daemon thread:
HFP_RE = re.compile(r"(?:modem not available|RFCOMM event): (AT\S*)")
HFP_KEYS = ("AT+CHUP","AT+BVRA","ATA","AT+CKPD","AT+BLDN","ATD")
def hfp_watch(st):
  cmd=["journalctl","--user","-u","wireplumber.service","-f","-n","0","-o","cat"]
  last=("",0.0)
  while True:
    p=subprocess.Popen(cmd,stdout=subprocess.PIPE,text=True,bufsize=1)
    for line in p.stdout:
      m=HFP_RE.search(line)
      if not m: continue
      at=m.group(1).strip(); now=time.monotonic()
      if at==last[0] and now-last[1]<0.5: continue  # INFO+DEBUG duplicates
      last=(at,now)
      note=on_press(st,source="hfp") if at.startswith(HFP_KEYS) else ""
      log(f"hfp at={at} phase={st['phase']} {note}")
    p.wait(); time.sleep(2)
Start it in main() next to the evdev loop. on_press is shared with the evdev path: AT+CHUP in 'recording' sets stop_evt; AT+CHUP in 'idle' starts a recording (this also covers the post-recording 'call' window from 5.5). 3) Make vad_wait honor stop without data: before each read call select.select([proc.stdout],[],[],0.2), check stop_evt and max_s, then os.read(proc.stdout.fileno(), chunk). This is needed because the speaker may drop SCO after the ERROR reply. 4) Unit test: feed the sample lines "spa.bluez5.native: RFCOMM receive command but modem not available: AT+CHUP" and "I spa.bluez5.native [backend-native.c:1433:rfcomm_hfp_ag]: RFCOMM receive command but modem not available: AT+BVRA=1" through the parser, and assert on_press is called with phase 'recording' → 'stop'.
  RISK: None. Read-only logging; PipeWire's replies to the speaker are unchanged. Cost: a few extra journal lines per SLC and per press.

## UNSOLVABLE
- (Making the stock speaker send AVRCP PASSTHROUGH while it believes a call is active.) Which message the button produces (AVRCP vs AT+CHUP vs nothing) is decided in the speaker firmware's key and state machine. BlueZ forwards whatever arrives (avctp.c:370-441) and has no SCO-dependent filter, so there is nothing on the host to unblock. The host can only change what the speaker believes: the dummy call through bluez5.disable-dummy-call, or the call-control replies in a patched or own AG.
  WOULD CHANGE: A hardware test with disable-dummy-call=true showing AVRCP events during SCO; or our own AG (or a patched PipeWire) sending +CIEV: 2,0 after AT+CHUP.
- (Custom firmware to change button behaviour (requested: "на уровне кастомной прошивки").) (1) There is no working delivery route: SPP-OTA is blocked by the bootloader-state catch-22, the SD path is retracted, USB DFU is unclear (ATS2831 vs JieLi AC690N topology), and JTAG or boot straps require opening the case (research/FIRMWARE.md:56-100). (2) The main SoC (Actions ATS2831) is NDA with no public SDK or symbols. The key table would have to be found by hand in a 1.18 MB binary (flag41007.bin), and even the vendor is disputed (bugzmanov says JieLi). (3) The only custom-code project (minitoo-forth) ran in simulation only, never on hardware (FIRMWARE.md:54). (4) No proven recovery after a failed flash (FIRMWARE.md:122); bugzmanov already soft-bricked a unit just by probing commands (FINDINGS.md:589-599). (5) It is probably unnecessary: if the speaker sends AT+CHUP, the host already receives the press and the watcher catches it.
  WOULD CHANGE: A demonstrated, reversible flashing route (for example a working DFU combination or HCI evidence for OTA bootloader state), a JTAG dump and restore procedure, and identification of the key-dispatch table.
- (Detecting a press that the speaker never puts on the air during SCO (if btmon or level-D logs show neither AVRCP nor RFCOMM traffic at the press).) Host software can only see packets that arrive. SCO carries audio only. SPP is not served by the firmware during SCO (HANDOFF §5.2), and no SPP key notification exists (FINDINGS.md:260-285). If the firmware handles the press locally (for example as mic mute), no Linux-side change can observe it.
  WOULD CHANGE: Changing the speaker state (disable the dummy call), another gesture that does emit traffic (volume → AT+VGS), or the firmware change above.
- (Reading the AT stream from stock PipeWire with zero configuration change and without root.) At default level N the relevant lines are INFO or DEBUG and are dropped (wireplumber log.c:210). The only outward effects of HF commands are volume and battery (backend-native.c:672-702, 1037-1065). ptrace and btmon need privileges, and the RFCOMM fd belongs to PipeWire alone. A user-level log setting is still enough (no root), so this is a limit only in the 'zero config' sense.
  WOULD CHANGE: The one-line `wpctl set-log-level` (user level) or an upstream PipeWire change that exposes HF key events.

There is also a third, weak SoC claim the report omits: 'Minitoo uses a SiFli SoC' (FINDINGS.md:1759). The FINDINGS.md:589-599 'brick' was recoverable by power-cycle (a soft brick), so it is weak support for firmware risk.

### solution concerns
- Solution 2 and the diagnostics say to reset with `wpctl set-log-level -`. module-log-settings maps NULL to wp_log_set_level("2") (module-log-settings.c:42-43), which removes ALL patterns, including the spa.bluez5.native:I that solution 1's conf.d fragment set at startup. After the diagnostic, the AT watcher goes silently blind until WirePlumber restarts. Reset with `wpctl set-log-level "N,spa.bluez5.native:I"` instead. The watcher should also re-apply that command at startup and whenever WirePlumber restarts (a new client id; the old metadata key does not carry over).
- Solution 1 treats AT+CHUP in phase 'idle' as 'start recording'. A firmware could send AT+CHUP on its own: on a call timeout, on SCO loss, or as a retry after the ERROR reply. That would start unwanted recordings. Ship it log-only first, or accept hfp-source starts only within N seconds after a recording ended. A cheaper filter is available: `journalctl --user -u wireplumber -f -o cat TOPIC=spa.bluez5.native` (the TOPIC field is written at wireplumber log.c:828-829).
- Solution 3 (disable-dummy-call): the JieLi analogue predicts both the upside and new side effects. The upside is that PP then sends AVCTP PLAY (bt_key_fun.c:451-452). The side effects: (a) volume keys during SCO without a call no longer send AT+VGS (bt_key_fun.c:177-187, 217-222), so solutions 3 and 4 exclude each other; (b) the firmware discards the first ESCO_DUMP_PACKET_CALL=120 eSCO packets when no call is active (soundbox bt.h:6-8, bt_event_fun.c:1533-1539, 1810, 1826), so the start of the 'Говорите' prompt may be cut more (HANDOFF 5.6). Also, the persistent rule example matches '~bluez_card.*', which changes behaviour for EVERY Bluetooth headset. Match the MiniToo address or name instead.
- Solution 4 (volume as a stop gesture) is not read-only in effect. A speaker-initiated AT+VGS changes the real HFP volume, and bluez5-device.c:413 sets node->save=true, so WirePlumber persists it. False positives are also likely: AG volume sync at SCO ready (backend-native.c rfcomm_ag_sync_volume) and the route and volume restore at profile switch both touch channelVolumes.
- Solution 6 (patched libspa-bluez5.so): sending +CIEV: 2,0 after AT+CHUP is likely to make the speaker close SCO, so pw-record then stalls. That needs the select-based vad_wait fix to land first. The build must also match Ubuntu's 1.6.2 patches and meson options (for example bluez5-backend-native-mm changes the +BRSF bits through mm_supported_features), because Ubuntu's libspa-codec-bluez5-*.so plugins will still load from the second SPA_PLUGIN_DIR entry. SPA_PLUGIN_DIR path walking itself is confirmed (pipewire.c:244, 518-520).
- Solution 7 (own Python AG) has a wrong API detail. CPython 3.14 BTPROTO_SCO addresses are a bytes or str bdaddr, not a tuple. `connect((mac,))` raises OSError 'connect(): wrong format' (https://raw.githubusercontent.com/python/cpython/3.14/Modules/socketmodule.c lines 2233-2261). Use `s.connect(mac.encode())`. socket.BT_VOICE and BT_VOICE_CVSD_16BIT do exist in 3.14 (lines 7995-7997), packed as struct 'H'. Role=server stops BlueZ from initiating HFP to the speaker. PipeWire passes no Role option (no 'Role' string in backend-native.c). An AG also has to send OK plus '+BVRA: 1' and then open SCO itself.
- The diagnostics reuse the old btdebug capture. The HANDOFF's suggested pattern `WIREPLUMBER_DEBUG=bluez5:4` (HANDOFF.md:115) would NOT have matched topic spa.bluez5.native, because WirePlumber and PipeWire match the whole string with a glob (wireplumber log.c:372-397; pipewire log.c update_topic_level uses fnmatch). An old capture may therefore contain no RFCOMM lines at all. Verify that before drawing conclusions from its absence.
- The hciconfig ACL-counter cross-check is noisy (SPP keepalive, AVDTP signalling) and the tool may be missing. Treat it as a hint, not a proof. btmon by the owner remains the only conclusive over-the-air test.

### missed
- Public JieLi soundbox SDK code (AC696N; local copy scratchpad/verify/jl/) shows the exact mechanism. In an active call, Play/Pause → HFP hangup (AT+CHUP); otherwise → AVCTP PLAY (bt_key_fun.c:442-454). The report said no JieLi or Actions key table could be found, yet this is the strongest available evidence for its central hypothesis and for the disable-dummy-call experiment.
- The HFP SLC (RFCOMM) stays connected while the card is in a2dp-sink, so the AT watcher also sees HFP gestures in idle mode. In the JieLi analogue, KEY_CALL_LAST_NO (a double click) → AT+BLDN when not in a call (bt_key_fun.c:533-552), and KEY_OPEN_SIRI → USER_CTRL_HFP_GET_SIRI_OPEN (AT+BVRA=1, bt_key_fun.c:586-589; dispatch at bt.c:936-970). Both would show up as 'modem not available' INFO lines today. That could give a separate 'talk' gesture (the user's walkie-talkie idea) with no AVRCP involvement.
- The report's AT-command mechanism is the HANDOFF's hypothesis 1 (key over HFP RFCOMM), not hypothesis 2 (AVRCP not served).
- SCO release is postponed by a further 1000 ms (bluez5-dbus.c:272, 3472-3477), which lengthens the post-recording 'fake call' window that matters for 5.5.
- The vendor question is wider than ATS2831 vs JieLi: FINDINGS.md:1759 also claims a SiFli SoC. The JL_* SDP service names suggest the Bluetooth stack is JieLi-based, and JieLi SDKs are public. The firmware infeasibility therefore rests on delivery and recovery and on the missing Divoom application source, not on a missing SDK.
- 5.1 evidence check: minitoo-talk-key.py:204 logs every EV_KEY event, so the HANDOFF observation 'no event during recording' already excludes an unhandled key code such as KEY_STOPCD as the cause.
- For any watcher or diagnostic, `wpctl set-log-level` survives only until WirePlumber restarts (the 'settings' metadata is keyed by the WirePlumber client id). After the HANDOFF's restart-WirePlumber recovery procedure (HANDOFF.md:150), the runtime setting is gone unless the conf.d fragment is installed.
