# firmware

## SUMMARY

Notation: S=/tmp/claude-0/-home-user-hermes-minitoo-gadget/12dc8b94-56a7-5220-9aa7-e289d63fc421/scratchpad; reference clones (read-only data) in S/ext2: jielie and jl-uboot-tool (github.com/kagaimiq), ac701n_soundbox (github.com/UWINGS-KUNYI/ac701n_soundbox @f8eeea1, a distributor-published copy of the JieLi JL701N soundbox SDK, licensing unclear, must not be vendored). Nothing was tested on hardware; tangled.org (minitoo-forth) was unreachable and no mirror was found, so minitoo-forth claims are known only via research/FIRMWARE.md. The ATS2831+AC690N premise is contradicted by several independent fingerprints that all point to a single JieLi BR28-family (AC701N/JL701N) chip running the Bluetooth stack and USB: DeviceID vendor 0x05D6 = Zhuhai Jieli, the SDP 'JL_SPP' record with UUID fe010000-… on RFCOMM channel 10 and BLE UUID 0xAF30 are identical to JieLi SDK records, and the USB function reports 'BR28 UDISK' with JieLi VID 0x4C4A. A matching SDK, datasheets and a Linux-capable toolchain are obtainable, and the SDK's update integrity is CRC-based rather than cryptographically signed, so cryptography is not the main barrier. The real barriers are: (1) Divoom's application layer (display driver, SPP display protocol, decoders, UI) is closed and not in any SDK, so a custom firmware means either reverse-engineering and patching Divoom's binary for a pi32v2 CPU with almost no decompiler support, or rebuilding the whole product firmware and losing/reimplementing the display stack; (2) the Bluetooth controller and host stack are closed binary libraries even inside the SDK, so link-level behaviour cannot be changed; (3) host-side problems cannot be touched by speaker firmware at all. Per problem: custom firmware could in principle fix (a) key routing during eSCO, (c) a fixed MAC, (e) stored state screens and (f) a mic stream over SPP (the SDK already contains an Opus mic-encoding pipeline), but only partially (b) and (d), and not (g). Every one of those has a far cheaper non-firmware route that should be tried first. Most important: a third-party report says the MiniToo's USB-C port exposes USB Audio (speaker + microphone) plus a HID consumer-control interface while the screen keeps working over Bluetooth SPP; the SDK's PC mode maps Play/Pause to a USB HID key. Using USB for audio and buttons removes HFP/SCO entirely, which is the trigger of (a), (b), (d) and the 8 kHz mic of (f). For (a) on Bluetooth, the SDK maps Play/Pause to HFP commands (AT+CHUP etc.) when a call is active, and PipeWire 1.6.2 without ModemManager rejects such commands and logs them only at INFO level, so a no-root log capture can show whether presses are arriving as AT commands; if so, a small host-side handler or PipeWire patch fixes it. For (g), the Intel 8087:0a2a is a 2014 legacy-ROM controller that Linux explicitly flags as not supporting wideband speech and that has no LE isochronous channels; speaker firmware cannot change this, replacing the adapter can. LE Audio is not a viable route (host adapter lacks ISO; the SDK's 'LE Audio' is JieLi-proprietary BIG/CIG with the JLA codec). Realistic firmware effort: weeks to months of skilled reverse engineering for even one patched behaviour, with non-zero risk to a battery-powered device, so firmware work is a research project, not a fix. Recommendation: test the USB path first (about an hour, no risk), run the AT-command capture, replace or stabilise the Bluetooth adapter, use stock custom-face switching for state screens, and do not pursue firmware modification unless all of these fail. Also, HANDOFF §6.3 over-reads AT+BRSF=671: it does not include enhanced call status/control or HF indicators.

## SOLUTIONS
- (5.1/5.3 (a) buttons during SCO) [diagnostic-first] hw_test=True
  APPROACH: First find out whether presses during SCO arrive as HFP AT commands; if they do, consume them on the host with no firmware change.
  IMPL: 1) Temporarily raise the WirePlumber log level (wpctl set-log-level I), start a recording, press Play/Pause short, long and double, then grep the wireplumber journal for 'RFCOMM receive command' and reset with wpctl set-log-level - (wpctl.c:1777-1850 supports '-' to reset). 2) If AT+CHUP/ATA/AT+BVRA/AT+BLDN show up: quick path = minitoo-talk-key follows the wireplumber journal with an INFO pattern for spa.bluez5 only and treats those lines as stop; robust path = a small patch in backend-native.c rfcomm_hfp_ag() that recognises these commands before the 'modem not available' branch and signals a FIFO/D-Bus event, built from the 1.6.2 tag as a local override. 3) If nothing arrives, the speaker emits nothing during eSCO: use the USB route instead.
  RISK: none
- (5.1/5.2/5.3/5.4/5.6 and (f) — eliminate HFP/SCO entirely) [implement-opt-in] hw_test=True
  APPROACH: Connect the MiniToo by a USB-C data cable to the server: speech output and microphone over USB Audio, buttons over USB HID; Bluetooth is used only for the SPP display link.
  IMPL: Verify enumeration (lsusb, arecord -l, wpctl status), record a test clip from the USB microphone, check that Play/Pause produces a USB HID input event (also during recording), and check that the SPP screen keeps working while in USB/PC mode. If it does: point config.json audio.output/audio.input to the USB nodes, make minitoo-talk-key match the USB HID device (KEY_PLAYPAUSE), and keep the Bluetooth audio card profile at 'off' (wpctl set-profile <card> 0, or a WirePlumber rule) so no SCO is ever opened, while RFCOMM for the screen remains. If PC mode stops Bluetooth or overrides the screen, this route fails for the display and must be dropped.
  RISK: low; the device charges continuously while connected (minor battery wear)
- (5.7 (g) host adapter) [implement-now-safe] hw_test=True
  APPROACH: Treat the host adapter as a separate problem: persist the autosuspend fix and replace the Intel 8087:0a2a with a current BT 5.x controller that Linux marks as wideband-speech capable.
  IMPL: udev rule, e.g. /etc/udev/rules.d/50-bt-autosuspend.rules: ACTION=="add", SUBSYSTEM=="usb", ATTR{idVendor}=="8087", ATTR{idProduct}=="0a2a", ATTR{power/control}="on" (or 'options btusb enable_autosuspend=0' in /etc/modprobe.d). Replacement candidates: Intel AX200/AX210-class (BT 5.x) or a dongle known to work with PipeWire mSBC; confirm with 'btmgmt info' (wide-band-speech) and the codec shown in wpctl inspect.
  RISK: none
- ((e) persistent state screens) [implement-opt-in] hw_test=True
  APPROACH: No firmware needed: use stock custom faces with ClockId switching or photo albums, and change the screen before SCO opens.
  IMPL: Upload the Hermes state faces once, then switch with Channel/SetClockSelectId (research/HACKS.md §4, verified upstream by bugzmanov). Send the 'Listening' switch before 'button talk press' (or use the USB route so SCO never interrupts the link). Avoid the sleep-family opcodes 0x40/0xa3/0xa4/0xad/0xae and the 0x3C custom icon (FINDINGS.md:587-599, 916-929).
  RISK: low (soft lock-ups recoverable by power-cycle if forbidden opcodes are sent)
- (5.8 (c) MAC address changes) [diagnostic-first] hw_test=True
  APPROACH: Diagnose before acting: determine whether the 'new' address is a regenerated BR/EDR address or a second identity of the same speaker; keep minitoo-autoaddr meanwhile.
  IMPL: List all MiniToo entries in bluetoothctl with Name/Alias/AddressType/Modalias/UUIDs, and note whether the change coincided with a reset, an app update or a long button combination. A firmware-level fix (pinning the factory MAC) would require writing the device's configuration area, so it is not recommended.
  RISK: none for diagnostics
- (5.2 (b) display channel lost during SCO setup) [diagnostic-first] hw_test=True
  APPROACH: Establish whether RFCOMM actually disconnects or the speaker just stops answering 0x8B while in call state; firmware could only help if the cause is Divoom's app layer (the SDK switches UI windows on SCO status change, bt_event_fun.c:1110-1114), which is closed.
  IMPL: Correlate hermes-minitoo logs ('did not send the 0x8B ready ACK', reconnects) with wireplumber 'lost RFCOMM connection' lines; if root is available, btmon around a press. Practical mitigation: avoid SCO (USB route) or send the frame before SCO opens and do not reconnect aggressively while the card is in headset-head-unit.
  RISK: none
- (5.4/5.6 (d) cut start of prompts) [implement-opt-in] hw_test=True
  APPROACH: Avoid profile switching rather than changing firmware: the switch is host-driven (exclusive PipeWire card profiles plus AVDTP stream restart), and the firmware's own A2DP buffering default is only about 200 ms.
  IMPL: Keep the 0.9 s pre-roll; better, remove switching via the USB route, or keep the Bluetooth card in headset-head-unit for the whole exchange (narrowband output, but no switch). Evidence: bluez5-device.c:59-67; S/ext2/ac701n_soundbox/sdk/apps/soundbox/log_config/lib_btctrler_config.c:128.
  RISK: none
- ((a)(c)(e)(f) via custom firmware) [not-feasible] hw_test=True
  APPROACH: Either patch Divoom's existing image (key handling during eSCO, fixed MAC, stored screens) or build a new firmware from the SDK reusing its mic->Opus->SPP pipeline. Both are reverse-engineering research projects, not fixes.
  IMPL: Not specified operationally on purpose. Effort estimate: a single patched behaviour in Divoom's pi32v2 binary is weeks to a few months for an experienced embedded reverse engineer with only a disassembler; a full replacement firmware needs board bring-up (LCD controller and pins, amplifier, charger/PMU, keys) and reimplementing the display protocol, i.e. 3–6+ months. Every test iteration requires writing flash on the owner's only unit.
  RISK: moderate: failed writes may be recoverable via the mask-ROM USB mode, but wrong charger/PMU configuration in a rebuilt firmware can damage the battery; warranty void
- ((f) LE Audio or A2DP-duplex microphone path) [not-feasible] hw_test=False
  APPROACH: Rejected: the host adapter has no LE isochronous channels, the SDK's LE Audio is proprietary (JLA codec, JieLi-to-JieLi), and A2DP duplex codecs are not offered by the closed JieLi stack.
  IMPL: None; use the USB microphone instead (see the USB route).
  RISK: none

## UNSOLVABLE
- ((g) Host adapter problems (Intel 8087:0a2a: no WBS, scan-disable EBUSY, corrupted SCO packets, autosuspend) via speaker firmware) These are host-controller firmware and kernel driver behaviours. Linux itself flags this legacy-ROM part as not WBS-capable (btusb.c:514-516, btintel.c:3776-3796). Nothing the speaker runs can change the host controller's ROM, its USB isochronous handling or its LMP feature set.
  WOULD CHANGE: Replacing the adapter with a current BT 5.x controller that Linux marks WBS-capable; persisting power/control=on via a udev rule.
- (Standard LE Audio (BAP/LC3) as a voice path) The host adapter is a BT 4.x-era part without isochronous channels; the SDK's 'LE Audio' is proprietary BIG/CIG with the JLA codec; and the BLE controller/host stack is a closed binary, so implementing standard BAP unicast on the speaker is impractical.
  WOULD CHANGE: Both a BT 5.2+ ISO-capable host adapter and a JieLi SDK release with standard BAP/LC3 unicast support plus a firmware built on it.
- (Changing link-level behaviour (eSCO vs ACL/RFCOMM scheduling) if the display stalls are controller-level) Even inside the SDK, btctrler/btstack are shipped only as binary libraries (95 .a files), so RF/LMP scheduling cannot be modified by a custom firmware.
  WOULD CHANGE: JieLi source access under NDA, or evidence that the stall is in Divoom's application layer rather than the controller.
- (A custom firmware that keeps all Divoom features (faces, gallery, app/cloud compatibility)) Divoom's application layer is closed; rebuilding from the SDK drops it, and binary patching keeps it only at large reverse-engineering cost on a CPU (pi32v2) with almost no decompiler support.
  WOULD CHANGE: Divoom publishing source or a documented extension interface, or a substantial community reverse-engineering effort.
- (Seamless high-quality A2DP output plus HFP microphone without any switch on Bluetooth Classic with PipeWire) PipeWire card profiles are mutually exclusive (bluez5-device.c:59-67); A2DP is unidirectional; A2DP duplex codecs (FastStream/Opus back-channel) are not offered by the JieLi stack.
  WOULD CHANGE: Moving the microphone off Bluetooth (USB Audio) — available on stock firmware according to third-party observation.

### solution concerns
- (a) The report misses the most likely root cause and the cheapest fix. PipeWire 1.6.2 sends a fake 'call active' indicator (+CIEV: 2,1) whenever it acquires the SCO transport (backend-native.c:2808-2810; rfcomm_hfp_ag_set_cind at :1067-1080; CIND order service,call,... at :1169-1174). The JieLi HF subscribes to these with AT+CMER=3,0,0,1 (string in btstack.a hfp_profile.c.o IR). So once recording starts, the speaker believes a call is ACTIVE and Play/Pause becomes AT+CHUP instead of AVRCP (bt_key_fun.c:472-484). The dummy call can be turned off with the documented device property bluez5.disable-dummy-call (pipewire-props.7.md:1146-1150; bluez5-device.c:3109-3112 at runtime via Props params, :3380-3381 at init via a WirePlumber monitor.bluez.rules update-props). This needs no root, no patch and no firmware change. It is an opt-in experiment because the doc warns some headsets time out SCO without a call. It should come before a journal-scraping handler or a PipeWire patch.
- (a) The proposed robust path, a patched backend-native.c 'built from the 1.6.2 tag as a local override', omits the mechanics. Replacing the distro libspa-bluez5.so needs root, or an SPA_PLUGIN_DIR override in the user wireplumber unit. The build must match Ubuntu's own build of 1.6.2 (distro patches, ABI), and any pipewire package upgrade silently breaks it. The quick path (scraping the journal) needs WirePlumber logging kept at INFO permanently, while HANDOFF.md:163 records that verbose BT logging caused flooding and instability.
- (a) The diagnostic grep pattern includes 'ATA', which also matches unrelated words such as 'DATA' and gives false positives. Match 'modem not available: ATA' or anchor the match on the command instead.
- (a) The cheapest decisive test is missing. In the SDK the joystick NEXT/PREV are sent as AVRCP regardless of call state (bt_key_fun.c, bt_key_music_prev/next just after :484). Pressing the joystick during a recording separates two hypotheses: if 163/165 arrive, AVRCP works under eSCO and only Play/Pause is call-remapped; if not, AVRCP is suppressed. Likewise, +/- during a call send AT+VGS (bt_key_fun.c:148-240), which PipeWire turns into a node volume change (backend-native.c, VGS handling near :1374-1382). That is a host-observable stop signal with no root needed (pw-mon or wpctl). Divoom's own mapping may differ, so hardware testing is required.
- USB route: 'wpctl set-profile <card> 0' is not persistent. WirePlumber restores saved profiles on reconnect and can auto-switch to headset when a client opens a BT source. A monitor.bluez.rules entry (e.g. device.disabled, supported by create-device.lua:31 in WP HEAD, or bluez5.roles/profile restrictions) is needed, and should be checked against the server's WirePlumber release, not HEAD. The route also changes the usage model (the gadget is tethered by cable), and the whole premise rests on a Windows-only docstring. Nothing confirms the USB microphone or HID behaviour on Linux, or that Divoom's PC mode keeps SPP alive.
- (g) The udev rule and modprobe option are correct (btusb module_param enable_autosuspend at btusb.c:4855), but installing either needs root. The report rates the risk as 'none' without stating that root is needed. 'Intel AX200/AX210-class' are M.2 combo cards, not USB dongles, and 8087:0a2a is itself the BT core of an Intel 7260/3160/7265/3165 combo card (btintel.c:3776-3777 WP/StP). Replacing it means swapping the internal card, or adding a USB dongle and disabling or unbinding the internal hci, then re-pairing on the new adapter.
- (e) The face-switching solution ignores the three-slot limit and the account-specific ClockIds that need the Divoom cloud token (FINDINGS.md:1590-1620). It also ignores the user's explicit 'оставь пока как есть' about Listening (HANDOFF.md:33,128); it is correctly marked opt-in. SetClockSelectId still travels over the same RFCOMM link that drops during SCO setup, so it only helps if sent before SCO opens.
- (d) The rationale cites firmware A2DP buffering of about 200 ms, but the non-EQ default is 340 ms (lib_btctrler_config.c:127-131).
- Firmware verdict and risk: 'failed writes may be recoverable via mask-ROM USB mode' needs custom dongle hardware and reset timing (usb-key.md), not just the USB-C cable. The flash tool also needs Divoom's chip key, or the download fails with a key mismatch (SDK README notes; download.bat:11). These should appear in the effort and risk estimate.
- Diagnostics: 'journalctl -k' needs adm or systemd-journal group membership on Ubuntu, and evtest on a new USB HID node needs input-group access on a headless server. Neither needs sudo, but the commands may fail without these permissions.

- The PipeWire dummy-call mechanism (+CIEV: 2,1 on SCO acquire, backend-native.c:2808-2810, 2863-2865) together with the JieLi HF's AT+CMER=3,0,0,1 subscription is the source-level link that turns Play/Pause into AT+CHUP during recording. bluez5.disable-dummy-call (pipewire-props.7.md:1146-1150) is a no-root, no-firmware experiment for (a). It may also help (b): in the SDK, an active call triggers phone-state handling (bt_event_fun.c:1653-1684, ui_update_status(STATUS_PHONE_ACTIV)), and Divoom's app layer may stall the SPP display in that state. That last part is a hypothesis.

- SPP_CHANGE_MODE 0x05 lists a UAC source mode (FINDINGS.md:85). It might switch the speaker into USB-audio mode over SPP for the USB route, but it is untested and should be treated as unprobed per the safety rules.
- Only three custom-face slots exist (ClockId 984/986/988), and they are account-bound (FINDINGS.md:1599-1620). This constrains the (e) alternative.
