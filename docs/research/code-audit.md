# code-audit

## SUMMARY

I audited every file listed against origin/main 21af541. I also read Hermes Gadget SDK v0.2.0 at commit 323e3303 (cloned from GitHub; it is the same commit HANDOFF names), BlueZ 5.85, WirePlumber 0.5.13/HEAD and systemd v258. Every defect below was reproduced on synthetic input (no hardware). The worst real bugs: (1) talk-key vad_wait blocks forever if pw-record delivers no data. max_s and stop_evt are only checked after a blocking 3200-byte read, so the worker wedges in 'recording' and the talk button stays held until Hermes core auto-finishes after 30 s. (2) VAD calibration on the first 0.8 s turns HFP start-up garbage (RMS 2594) into a 7781 threshold, giving 'речи нет', which is exactly HANDOFF §8.3. (3) autoaddr rewrites the token-bearing config.json (and its .bak) with umask mode, 0644 instead of 0600. Its str.replace only fixes MACs written with colons; WirePlumber's real node names use underscores, and only the loopback nodes keep colons. (4) config.py rejects minitoo.retry_window_s and any top-level talk_key section. Adding either key, as the docs suggest, would crash hermes-minitoo in a restart loop. Smaller proven defects: a failed or timed-out press skips the release; there is no SIGTERM handling; the CLI's errors go to stdout while talk-key logs stderr (so reasons are empty); a debounce race; find_event takes the first matching device and never rescans; ensure_wav has a fixed /tmp path, a non-atomic WAV and is fatal when TTS fails; the transport leaves the leftover ACK deadline as the socket timeout for chunk writes; display.close() closes the socket under a still-running worker; StartLimitIntervalSec sits in [Service], where systemd ignores it; hard-coded /home/bishop paths; CI tests only 3.12. The dead indicator code is provably a no-op when ~/.cache/minitoo-indicator is absent, and nothing on main writes that file. Removing it cannot change behaviour, and simulated frame timing was identical. The control socket can be used directly: the SDK protocol is one JSON line over <state_dir>/control.sock, and the 0.5–1 s comes from the CLI's interpreter start plus imports. I built a defaults-preserving prototype patch: /tmp/claude-0/-home-user-hermes-minitoo-gadget/12dc8b94-56a7-5220-9aa7-e289d63fc421/scratchpad/verify/section8-fixes.patch. It applies cleanly to 21af541, and 44 tests pass on Python 3.13 and 3.14. A randomized check (400 streams) shows the refactored VAD makes byte-identical decisions with default settings. Hardware-touching changes are opt-in only (env MINITOO_* or config talk_key.*): direct socket control, the adaptive VAD (warm-up, rolling noise floor, detection that also counts speech heard before the floor settled), cancel-during-prompt, and autoaddr RSSI/name/one-shot modes. Reproduction scripts are verify_bugs.py, vad_equivalence.py and vad_optin.py in the same verify/ directory; the prototype tree is scratchpad/work. Two things this code cannot fix. Stopping a recording with the speaker button depends on §5.1: no key events reach evdev during HFP. Choosing VAD thresholds needs real RMS traces, which the prototype now logs per recording. Two hypotheses explain HANDOFF §5.5 ('first press does nothing'). First, the SDK silently cancels a recording on any PortAudio input status flag. Second, a press can be accepted while the gadget is not in a state to listen. talk-key cannot see either today; the prototype logs gadget status (read-only) after press and after the VAD stops.

- [documented-by-third-party/medium] The device answers an 0x8B upload with chunk requests '8b 55 01 <idx_u16>'. minitoo-control clears its RX buffer before each announce and requires a final ACK (04 bd 55 13 01 05 00 on its 128x128 zstd path); the .NET client registers its waiter before announcing. ## UNSOLVABLE
- (5.3: stopping a recording with the speaker button, by changing talk-key) talk-key already reads evdev continuously in its own thread while recording (main loop talk-key:173-204; the worker runs in a separate thread, :159), and on_press already maps a press in 'recording' to stop_evt (:161-163, unit-tested). HANDOFF §5.1 (verified on hardware) says no EV_KEY event at all reaches the AVRCP uinput device while the card is in headset-head-unit. BlueZ only writes to uinput when an AVRCP PASSTHROUGH arrives on the AVCTP channel (avctp.c:378-430). No code in this repo can produce an event the kernel never receives. The non-blocking reader in the patch only guarantees that a stop would work if an event arrived during a stalled stream.
  WOULD CHANGE: A btmon capture during a press in HFP showing where the press goes. If it is AT+CKPD/AT+BVRA on the HFP RFCOMM channel (PipeWire backend-native.c handles AT commands), a PipeWire/WirePlumber hook or patch could turn it into an event (other agents' topic). If nothing is sent at all, only a firmware change could help, and HANDOFF §9.3 documents every firmware delivery route as blocked or unproven.
- (Choosing VAD thresholds and the warm-up length without hardware) The real RMS of the MiniToo's mSBC/CVSD mic, the duration of the SCO start-up garbage (only one value, 2594, is in HANDOFF) and how much 'Говорите!' echo reaches the mic are unknown. My simulations use synthetic sine tones and show only that the algorithm handles the shapes described in HANDOFF, not that any particular number is right.
  WOULD CHANGE: About 10 real recordings with the patch's per-recording 'VAD rms(100мс)=[...]' journal line (first 4 s), or MINITOO_VAD_* settings tried live. Then set vad_warmup_s just past the garbage and confirm vad_floor/mult against real speech RMS.
- (Proving that an uploaded frame was actually displayed (part of 5.2)) The transport has no completion check, and the local sources do not document the final acknowledgement for the native 160x128 0x23 live payload. minitoo-control documents 04 bd 55 13 01 05 00 only for its 128x128 zstd path (MiniTooTransport.swift:8); FINDINGS documents per-chunk requests '8b 55 01 <idx>' (FINDINGS.md:1065,1079-1080). Making failure-on-missing-ACK the default would change verified screen behaviour.
  WOULD CHANGE: DEBUG logs from the patch's _drain_stale summary on real hardware, to see which replies follow a successful upload. After that, an opt-in strict mode that waits for the observed final ACK.
- (autoaddr: identifying 'my' MiniToo robustly if the BR/EDR address really changes) BlueZ exposes only name/alias/class/Modalias, and these are identical for every MiniToo. RSSI is volatile and BlueZ reports it only on changes of at least 8 dB (device.c:79,6899-6930). With two MiniToos in range no heuristic in the script can tell them apart. FINDINGS mentions a periodic keepalive payload and an identity probe that might carry a device id (FINDINGS.md:262-267, 1180-1185), but that is unverified and reading it would mean opening RFCOMM to candidate devices.
  WOULD CHANGE: Confirming why the address changes (factory reset? firmware 'random address' option?). Or a verified device-unique id readable over RFCOMM, recorded in config and checked before rewriting it. Or a manual confirmation step, e.g. a Telegram prompt.
- (Making the 'Listening' frame appear by speeding up the button call (part of 5.2, 8.10)) Using the control socket directly removes only the CLI's interpreter start (~0.5-1 s) before the press. The profile switch that drops RFCOMM starts inside the press handler itself (app.cpp:825-829 start_listening -> hal_.mic->start -> SDK Audio.mic_start opens the bluez_input stream). The Listening frame is queued in the same service-loop iteration, at most 2.5 s later because of the update_interval throttle (display.py:82). Faster control therefore improves responsiveness, but not delivery of that frame.
  WOULD CHANGE: A display-side change (5.2 topic): send/confirm the frame before the mic opens, or use a persistent on-device image/command instead of an 0x8B upload during the switch.

### solution concerns
- Opt-in cancel policy (MINITOO_PRESS_DURING_START=cancel) with the default control='cli' can open the on-device SETTINGS MENU. The prototype sends cancel press and cancel release as two CLI invocations while talk is held (work/scripts/minitoo-talk-key.py:408-411). The core opens settings when talk and cancel have both been held ≥1000 ms (ext2/sdk/firmware/core/src/app_settings.cpp:137-144), and one CLI call costs ≈0.5-1 s on the N3700 (HANDOFF §8.10). Once the menu is open, the next talk release runs a menu item (volume, talk mode: app_settings.cpp:70-89). Holding cancel ≥2 s without talk starts a new session (app.cpp:1301-1306). The cancel policy, and any future 'cancel on shutdown', must require control=socket or send both events from one process back to back.
- Adaptive VAD: the suggested first trial (vad_adaptive, warm-up 0.5 s, min_speech_chunks 2) turns any garbage that outlasts the warm-up into 'speech'. When the noise floor drops, _last_loud re-scans the history (work/scripts/minitoo-talk-key.py:180-199, :255-257). If the user pauses more than silence_s before speaking, the recording stops before they speak. My simulation (S/vfy3/vad_optin_mine.py, same harness): 0.9 s garbage + 2 s pause + speech gives 'тишина после речи' at ≈2.5 s, before any speech. The report's scenario set lacks this case, and its 0.5 s warm-up is below HANDOFF §8.3's own '0.5–1 s' garbage estimate. Count only loud runs that come after the floor settles, or keep warm-up ≥1 s until real traces exist.
- SIGTERM fix: stopping or restarting the service mid-recording now sends 'release', which runs finish_listening (app.cpp:776-783), so a partial utterance goes to Hermes as a real turn. Discarding (cancel while talk is held) is the conservative choice for a shutdown, but it needs socket control because of the chord hazard above.
- transport._drain_stale is presented as removing a stale-ready-ACK false positive. In the current code that case is close to impossible: failures close the socket (transport.py:159-162) and a successful wait consumes the ACK. Its value is diagnostic only. It is still low-risk, and it handles EOF (patch line 1176-1177).
- transport.abort() cannot wake a worker blocked inside _open_rfcomm, because self.sock is None until connect returns. There is also a window between connect()'s _aborted re-check and 'self.sock = sock' in which close() can run first and leak the new socket until the process exits. Shutdown-only; the report's 'refuses … closes a socket that finished connecting' is not airtight.
- The patched minitoo-talk-key.service comment says 'see talk_key section in README', but the patch contains no README or docs change. The 'docs' solution is marked implement-now-safe but was not done, so the env/config options are undocumented for the owner.
- After=piper-tts.service in a USER unit has no effect if piper-tts is a system unit. HANDOFF §2 does not say which it is; unverifiable.
- talk_mode=tap experiment: the settings menu (talk+cancel chord over the control socket) is a safer route than hand-editing device.json, which also holds device_key and token (client.py:113-115). If tap mode is tried, talk-key should not play 'Говорите!' after the press. The core VAD (min 500 RMS, 200 ms of speech then 900 ms of silence, vad.cpp:42-50) can end the utterance on prompt echo or start-up garbage before the user speaks.
- Diagnostics: 'journalctl -k' needs adm/systemd-journal group membership or sudo, and HANDOFF §5.1 says the owner does not want sudo going through the bot. The udev rule and the chmod advice also need root or owner action and hard-code user 'bishop'.
- CI '-W error::ResourceWarning' does not catch ResourceWarnings raised in __del__/GC. pytest reports those as PytestUnraisableExceptionWarning without failing, so the check is only partly effective (minor).
