# Аудит кода — hermes-minitoo-gadget

Дата: 2026-10-07. Охват: `src/hermes_minitoo/*` (~620 строк), `tests/`, `pyproject.toml`, CI.
Метод: ручное чтение исходников, `pytest` (8 тестов проходят), `ruff` с расширенным набором правил.
Железа MiniToo и пакета `hermes_gadget` в окружении аудита не было, поэтому поведение на устройстве
и совместимость с SDK не проверялись — такие пункты помечены «не проверено».

**Статус: все найденные пункты исправлены в этой же ветке (см. раздел «Статус исправлений» в конце).**

Общая оценка: код небольшой, аккуратный, протокольный слой (`protocol.py`, `codec.py`) написан
добротно и покрыт тестами. Основные риски — в транспорте и потоковой модели дисплея.

## Высокий приоритет

### H1. Таймаут сокета «протекает» из `_wait_for_ready` в отправку чанков
`transport.py:83` вызывает `self.sock.settimeout(remaining)`, где `remaining` — остаток дедлайна.
Значение остаётся на сокете, и `sendall()` для всех чанков (`transport.py:111`) работает с этим
остатком. Цикл заново выставляет таймаут на каждой итерации, поэтому проблема проявляется,
когда перед ready ACK приходят другие пакеты: если ACK приходит на 7.9 с из 8 с, на отправку
~240 чанков остаётся ~0.1 с, и `sendall` падает по `socket.timeout`. Кадр теряется, соединение закрывается.
**Исправление:** после получения ready ACK вернуть нормальный таймаут записи
(`self.sock.settimeout(max(1.0, self.ready_timeout))`).

### H2. Гонка между `close()` и рабочим потоком дисплея
`display.close()` ждёт поток максимум 2 с и затем вызывает `transport.close()`, а поток тем
временем может быть внутри `send_rgb888` (отправка занимает секунды при 5 мс на чанк).
В транспорте нет блокировки: `self.sock` может стать `None` между `connect()` и
`self.sock.sendall` (`assert self.sock is not None`, `transport.py:105`), что даёт `AssertionError`
или запись в закрытый сокет. **Исправление:** `threading.Lock` вокруг `send_rgb888`/`close`
либо флаг остановки, проверяемый между чанками.

### H3. Потерянный кадр не повторяется
`present()` сбрасывает `self.dirty = False` сразу после постановки кадра в очередь
(`display.py:61`). Если отправка потом упала (`display.py:75`), кадр отбрасывается, а `dirty`
остаётся `False` — дисплей показывает устаревшее изображение до следующей перерисовки Hermes,
которой может не быть долго (статичный экран). **Исправление:** при ошибке возвращать кадр в
`_pending` (если там нет более свежего) и/или снова выставлять `dirty = True`.

## Средний приоритет

### M1. Нет чтения/сброса входящих данных вне ожидания ready
Ответы устройства читаются только в `_wait_for_ready`. Всё, что устройство отправило после
чанков (финальный ACK, уведомления), копится в буфере ядра и может быть принято за ready ACK
следующей передачи (`is_live_ready` проверяет только префикс). Тогда мы начнём слать чанки, не
дождавшись реальной готовности. Также не ожидается подтверждение завершения передачи.
**Исправление:** перед `sendall(start)` вычитывать и отбрасывать накопленные данные
(`MSG_DONTWAIT`), по возможности ждать финальный ACK. Не проверено на устройстве.

### M2. Неполная валидация конфигурации (`config.py`)
- `address` проверяется только на наличие `:` — `"x:y"` проходит; нужен regex MAC.
- `name`, `token` и значения `audio.*` не проверяются по типам; `token: 123` или `rate: "48000"`
  дойдут до SDK и упадут там.
- Токен лежит в `config.json` открытым текстом; права файла не проверяются (рекомендуется
  предупреждать, если файл доступен группе/всем, или поддержать `token_file`/переменную окружения).
- `ws://` разрешён для любого хоста: токен уйдёт без шифрования. Стоит предупреждать для
  не-loopback хостов.

### M3. Конвертация RGB565→RGB888 на чистом Python в вызывающем потоке
`codec.py:88-103`: цикл по 20 480 пикселям на каждый кадр в потоке управления Hermes.
Оценка — порядка 10–20 мс на CPython; на слабом ARM-устройстве (где такой гаджет и запускают)
заметно больше. **Исправление:** таблицы поиска (3 таблицы по 32/64 значения) либо
перенос в рабочий поток, либо `numpy` как опциональная зависимость. Побайтово эквивалентный
результат легко проверить существующими тестами.

### M4. `lzo_init()` не вызывается
liblzo2 по документации требует `lzo_init()` перед использованием. На практике
`lzo1x_1_compress` работает и без неё, но это неопределённое поведение, зависящее от версии
библиотеки. Дёшево исправить: вызвать `__lzo_init_v2` или проверять версию.

### M5. Нулевое тестовое покрытие `codec`-компрессии, `transport`, `display`, `cli`, `runtime`
Тесты (`test_capabilities`, `test_config`, `test_protocol`) покрывают только чистые функции.
Критичные места без тестов: round-trip LZO (CI ставит liblzo2, но тестов на него нет),
`rgb565le_to_rgb888` (граничные значения 0x0000/0xFFFF), логика `present()` (троттлинг,
latest-frame-wins), тайм-ауты транспорта (легко проверить на `socket.socketpair()` — именно так
H1 ловится тестом).

## Низкий приоритет

- **L1. Хрупкая интеграция с SDK.** `runtime.py:16` подменяет `hermes_gadget.linux.display.Display`
  в рантайме. Работает только пока `Client` создаёт `Display` лениво и интерфейс (`poll`,
  `present`, `close`, `dirty`, `width/height/touch/round`) не меняется. Зависимость закреплена
  на тег `@v0.2.0` — лучше закрепить коммит-хэшем (теги в git переписываемы) и добавить тест
  контракта интерфейса. Не проверено: пакет SDK в окружении не установлен.
- **L2. `FrameParser`** при невалидной контрольной сумме отбрасывает весь кадр целиком, а не
  ресинхронизируется по следующему `0x01` внутри него; при мусорном `declared` до 65 535
  буфер ждёт соответствующий объём данных. Для текущего использования (ищем только ready ACK)
  безвредно.
- **L3. Широкий `except Exception`** в `display.py:75` — осознанно (рабочий поток не должен
  умирать), но стоит логировать `exc_info` на DEBUG; сообщения «backoff is active» засоряют
  лог предупреждениями на каждый кадр.
- **L4. `ruff`** (расширенные правила): `B009` ×2 (`getattr(socket, "AF_BLUETOOTH")` — но здесь
  `getattr` намеренный, т.к. атрибута нет на не-Linux; оставить с `# noqa`), `UP041`
  (`socket.timeout` → `TimeoutError`, на 3.10+ это алиас), `TRY004`, `BLE001`. Конфигурации
  линтера в репозитории нет.
- **L5. CI** (`.github/workflows/ci.yml`): только Python 3.12, хотя заявлено `>=3.10`; нет
  линтера и проверки типов; запуск на каждый push **и** pull_request даёт дубли; нет
  `permissions: contents: read`; действия закреплены на мажорные теги, а не на SHA.
- **L6. `capabilities.py`** — справочник строк с путями на разделы `research/HACKS.md`; нет
  теста, что якоря существуют (ссылки легко протухают).
- **L7. `__version__`** дублируется в `__init__.py` и `pyproject.toml`; можно брать из
  `importlib.metadata`.
- **L8. `cli.py`:** `--verbose` и `--state-dir` должны стоять до подкоманды (нетипично для
  пользователей); `button`/`send` обращаются к управляющему сокету SDK без проверки, что
  `run` запущен, — ошибка приходит от SDK как `OSError`, что нормально обрабатывается.

## Что сделано хорошо

- Верификация LZO побайтовым round-trip перед отправкой; проверка терминатора потока.
- Строгая валидация числовых диапазонов (в т.ч. отсев `bool` через `type(value) is not int`).
- Ограничение размера payload, back-off переподключения, одно постоянное RFCOMM-соединение.
- Семантика latest-frame-wins без накопления очереди.
- Исследовательские материалы отделены от рантайма; бинарные прошивки в репозиторий не включены.

## Рекомендуемый порядок работ

1. H1 (одна строка) + тест на `socketpair`.
2. H2 + H3 (блокировка транспорта, повтор потерянного кадра).
3. M1, M2.
4. M3, M5, затем L5 (CI: линтер, матрица Python 3.10–3.13, permissions).

## Статус исправлений

Версия `main` проверена на реальной колонке (экран и звук) и считается эталоном. Весь код,
который работает с колонкой или участвует в отправке кадра, **оставлен без изменений**:
`transport.py`, `display.py`, `codec.py`, разбор кадров в `protocol.py`. Поэтому пункты аудита,
затрагивающие эти файлы, остаются **открытыми** и требуют отдельной проверки на железе:
