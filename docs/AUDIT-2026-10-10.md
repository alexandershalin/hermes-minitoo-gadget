# Аудит ветки `main` (v0.2.1), 2026-10-10

Проверялась ветка `main` на `9a2ac84` («Release 0.2.1: repository renamed to hermes-gadget-minitoo»). Главный вопрос — совместимость с подключённым Hermes Gadget SDK `v0.2.0` (коммит `323e330`). Работа вручную, без агентов; тесты — один прогон на системном Python 3.13.

## Совместимость с SDK: сохранена

- **Импорты из SDK** — только `hermes_gadget.__version__`, `hermes_gadget.sim.native.BUTTONS`/`NativeDevice` и `hermes_gadget.sim.transport.WsTransport`. Всё это есть в `323e330`.
- **`NativeDevice(...)`** — все аргументы, которые передаёт `client.py`, есть в сигнатуре конструктора SDK (`width`, `height`, `board`, `firmware`, `name`, `mic`, `speaker`, `mic_rate`, `speaker_rate`, `audio_host`, `backlight`, `scroll_buttons`, `button_labels`, `touch_screen`, `round_panel`; теперь и `library`).
- **Протокол `AudioHost`** — `audio.Audio` реализует все восемь методов, которые ядро вызывает (`mic_start`, `mic_stop`, `speaker_begin/write/end/abort/busy/volume`). Это класс `hermes_gadget.linux.audio.Audio` с теми же сигнатурами плюс сигналы для дисплея.
- **Протокол `Host`** — `client.Client` реализует те же методы, что клиент самого SDK (`hermes_gadget.linux.client`). `display_backlight` и `update_*` нет ни там, ни здесь: ядро зовёт их через `_guard`, и при `backlight=False` и без OTA они не вызываются.
- **Управляющий сокет** — `control.py` совпадает с `hermes_gadget.linux.control` построчно, кроме вынесенного `device_lock` (`platforms/linux/lock.py`, тот же код). Формат запросов для talk-key не изменился.
- **Проверка на настоящем SDK.** SDK установлен из чекаута `323e330` (`pip install -e`): 270 тестов проходят. Нативная библиотека ядра (`libhgsim`) в окружении аудита не собрана, поэтому вызовы ядра проверены сверкой с исходником `hermes_gadget/sim/native.py`, а не запуском.

## Код с прошлого ревью

`display.py`, `codec.py`, `protocol.py`, `platforms/linux/transport.py` и `platforms/linux/linkstate.py` по содержанию совпадают с версией, прошедшей ручное ревью (ветка PR 7). Изменились только импорты и путь пакетов, плюс в транспорте `last_failure = -inf` (исправление «первое подключение отклонено» из 0.1.2). Хуки `listen_preroll` перенесены из подмены методов SDK прямо в `audio.Audio`: так надёжнее, чем раньше.

## Что исправлено в этом аудите

1. **Переименование репозитория и пути по умолчанию.** На сервере каталог прежний (`~/hermes-minitoo-gadget`), и там ничего не меняется. Но при новой установке в каталог с другим именем (по умолчанию теперь `hermes-gadget-minitoo`) talk-key и диагностика искали `config.json` в `~/hermes-minitoo-gadget`: `install.sh` подставлял путь только в юниты.
   - `install.sh` пишет drop-in `minitoo-talk-key.service.d/00-repo.conf` с `MINITOO_REPO=<каталог чекаута>`.
   - `scripts/diag/_lib.sh` и `scripts/diag/links.py` берут `config.json` из репозитория, где лежит скрипт; если его там нет — прежнее место. `MINITOO_CONFIG` по-прежнему главнее.
2. **`client.Client(library=...)`** принимал путь к библиотеке ядра, но не передавал его в `NativeDevice`. Теперь передаёт, как клиент SDK. При `library=None` (как сейчас вызывает `control.run`) поведение то же.

## Что сознательно не менялось

- Имя Python-пакета `hermes-minitoo-gadget` и каталог состояния `~/.local/state/hermes-minitoo-gadget`: смена имени пакета ломает установленный venv, а смена каталога состояния — сопряжение с Hermes (`device.json`).
- Пути `~/hermes-minitoo-gadget` в комментариях юнитов и докстрингах: это реальный путь на сервере владельца, а `install.sh` их подменяет.
- Логика дисплея, транспорта и talk-key: она уже проверена ревью и на железе, рефакторинг ради рефакторинга не делался.

## Что осталось открытым

- Нативное ядро SDK не собиралось в окружении аудита: полная проверка — `install.sh` (собирает `libhgsim`) и прогон тестов на сервере.
- Новые opt-in опции и `install.sh` на чистом хосте на железе не проверялись.
